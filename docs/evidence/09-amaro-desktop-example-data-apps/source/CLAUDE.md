# CLAUDE.md — example-data-apps

400 synthetic Amaro data apps under [`apps/<category-slug>/<app-slug>/`](apps/), grouped into 17 categories. Plus a flat machine-readable [`apps.json`](apps.json) index, per-category READMEs ([`apps/<category-slug>/README.md`](apps/)), and a 9-prompt ranking benchmark under [`questions/`](questions/). Generated by Codex (the Synthetic Data Lab pipeline) — not hand-authored. Full index + layout reference in the sibling [`README.md`](README.md).

## What you can safely do here

- **Read** any app dir as a fixture for tests, screenshots, or local desktop demos.
- **Reference** slugs and category-slugs from other docs / runbooks / tests.
- **Regenerate** the per-category READMEs and `apps.json` with `python3 scripts/build_index.py`.
- **Use the questions TSV** as a regression benchmark for app-ranking / chat-routing.

## What NOT to do

- **Don't hand-edit** an individual app dir to fix a typo or relabel a category. The next regen of the synthetic-data-lab pipeline blows your edit away. If a category label is wrong, fix it at the generator.
- **Don't add a new app dir by hand.** Same reason — regen-only repo. If you need a new shape that the lab doesn't produce, file a request against the generator project, not against this repo.
- **Don't ship the prose / numbers verbatim** to a customer-visible surface. The data is realistic enough to look proprietary at a glance — that's by design for screenshot fidelity — but it's synthetic. Ship it for shape, not for substance.
- **Don't commit raw `data.json` blobs.** They're LFS-tracked via `**/data.json` in `.gitattributes`. Bypassing LFS (e.g. `git add --no-filter`) blows past GitHub's 50 MB recommendation; the largest data file is ~98 MB.

## Git LFS

Every app's `data.json` (and its mirrors under `ui/data.json` and `runs/<id>/data.json`) is LFS-tracked. After cloning:

```bash
git lfs install   # one-time per machine
git lfs pull      # materialize data.json files for current branch
```

Without an LFS pull, every `data.json` is a ~130-byte pointer stub and `app.py` will fail to read its inputs. ~540 MB of LFS objects total; fresh clones consume that against `oramasearch`'s monthly LFS bandwidth quota — confirm paid data packs before adding this submodule to CI that clones often.

## Categories — derivation

Each app's category comes from `meta.json` → `events[]` where `type == "plan_updated"` and `detail` matches `^(Created|Generated) for (.+)$`. The captured group after "for" is the category label.

Two label variants existed in the original corpus for the cross-functional bucket (`/` vs `and` separator). The script in `scripts/build_index.py` normalizes them to the canonical **Cross-Functional and Special Purpose** label via the `LABEL_ALIASES` map. If a new variant appears in a future regen, add it there — don't try to patch individual `meta.json` files.

The 17 canonical category labels and their directory slugs are in `scripts/build_index.py` → `CATEGORY_SLUGS`. Anything not in that map gets an auto-slug (lowercase, non-alphanumeric → `-`).

## Regenerating the index

```bash
python3 scripts/build_index.py
python3 scripts/validate_index.py    # optional but cheap
```

What `build_index.py` does:

1. **Move** (one-time) — if `data_app_synthetic/` still exists at the repo root, `git mv` each `<slug>/` into `apps/<category-slug>/<slug>/`. Skipped if `data_app_synthetic/` is gone.
2. **Per-category READMEs** — overwrite `apps/<category-slug>/README.md` for every category with a table of `[slug](slug/)` — name — description, sourced from each app's `spec.json`.
3. **Flat index** — rewrite `apps.json` at the repo root. Schema is formalized in `apps.schema.json` (JSON Schema Draft 2020-12); the file's `$schema` field points at it so IDE auto-validation works.

Idempotent. Re-run any time the corpus changes.

`validate_index.py` runs the schema check plus four cross-field integrity checks (total vs. category-sum, slug uniqueness, category cross-reference, per-category counts). Use it as a pre-commit hook or CI gate.

## `questions/` — ranking benchmark

`questions/data_app_synthetic 2 Questions to Ask - Sheet1.tsv` (9 rows + header) holds expected-top-N app matches for natural-language prompts. Use as regression coverage for any code path that ranks data apps from a question — `search_data_cache`, the chat-routing planner, the in-development LLM-driven app-discovery flow.

The expected-apps column references apps by **`name`** (e.g. "Cold Storage Temperature Monitoring"), not by slug. Cross-walk via `apps.json` → match `apps[].name`.
