# example-data-apps

400 synthetic Amaro data apps, generated by Codex against the Amaro Synthetic Data Lab spec. Use them as fixtures for UI screenshots, demo data, end-to-end tests against the desktop app, and as starting points for real customer apps.

This is a private repo — synthetic but realistic enough to look proprietary at a glance. **Don't post screenshots or share dirs externally.** Don't paste prose / numbers into customer-visible surfaces.

## Layout

```
.
├── apps/                              # all 400 data apps, grouped by category
│   ├── <category-slug>/
│   │   ├── README.md                  # category index — table of name + description
│   │   └── <app-slug>/                # one directory per app, identical inventory
│   │       ├── spec.json              # IR scaffold + name + description + dataSources
│   │       ├── app.py                 # generated Python pipeline
│   │       ├── data.json              # synthetic input data (LFS-tracked)
│   │       ├── meta.json              # author / category / event log
│   │       ├── instructions.json      # natural-language seed prompt
│   │       ├── steps.json             # plan steps (planner IR)
│   │       ├── actions.json           # configured triggers / actions
│   │       ├── action-history.jsonl   # append-only firing log
│   │       ├── audit.json             # per-run audit trail (six v2 risk categories)
│   │       ├── fidelity.json          # per-run Fidelity Score envelope
│   │       ├── rules.json             # business rules wired into the app
│   │       ├── shares.json            # sharing / permission state
│   │       ├── executions.json        # run history index
│   │       ├── runs/<run-id>/         # per-run artifacts
│   │       └── ui/                    # saved canvas / chat / briefing view state
│   └── … (17 categories)
├── apps.json                          # flat machine-readable index of all 400 apps
├── apps.schema.json                   # JSON Schema (Draft 2020-12) for apps.json
├── questions/                         # benchmark prompts for app-ranking evaluation
│   └── data_app_synthetic 2 Questions to Ask - Sheet1.tsv
└── scripts/
    ├── build_index.py                 # rebuilds apps.json + per-category READMEs
    └── validate_index.py              # validates apps.json against apps.schema.json + integrity checks
```

If you're loading an app into the desktop, the entry point Amaro reads is `spec.json` + `app.py`; the rest hydrates the surrounding chrome.

## `apps.json` — machine-readable index

`apps.json` at the repo root has every app as a flat record. Useful for building UIs, search, ranking benchmarks. Schema:

```jsonc
{
  "generated_at": "2026-04-29T01:46:00+00:00",
  "total": 400,
  "categories": [
    { "label": "Operations / Logistics", "slug": "operations-logistics", "count": 40 },
    …
  ],
  "apps": [
    {
      "slug": "account-health-scorecard",
      "name": "Account Health Scorecard",
      "description": "Composite score: volume trends, ticket frequency, NPS, payment status. …",
      "category": "Customer Success / Account Management",
      "category_slug": "customer-success",
      "path": "apps/customer-success/account-health-scorecard/",
      "ir_version": "3.0",
      "data_sources": ["salesforce-account-", "zendesk-account-", …]
    },
    …
  ]
}
```

The full schema is formalized in [`apps.schema.json`](apps.schema.json) (JSON Schema Draft 2020-12). `apps.json` carries a `$schema` field pointing at it so editors with JSON Schema support (VS Code, JetBrains, etc.) auto-validate while you type. Programmatic validation:

```bash
python3 scripts/validate_index.py
```

That runs the schema check plus four cross-field integrity checks the schema can't express alone — `total == sum(categories[].count)`, slug uniqueness, every `app.category_slug` matches a known category, and per-category counts match the actual app counts. Cheap; suitable as a pre-commit hook or CI gate before any consumer relies on `apps.json`.

Regenerate with `python3 scripts/build_index.py` — see "Regenerating the index" below.

## `questions/` — ranking benchmark

`questions/data_app_synthetic 2 Questions to Ask - Sheet1.tsv` holds 9 hand-curated benchmark prompts. Each row:

| Column | What |
|---|---|
| `#` | Row id. |
| `Prompt` | Natural-language question a user might ask. |
| `Apps AI Should Rank Highest` | Comma-separated list of expected top-N matches by `name`. |
| `Example Of A Good Answer` | Reference prose answer using actual data from the corpus. |

Use these as a regression test for app-discovery / `search_data_cache` / chat-routing logic — run the prompt through the pipeline, check the top-ranked app matches the expected list, optionally diff the answer against the reference for shape.

## Git LFS — required to materialize `data.json`

Every app's `data.json` (and its mirrors under `ui/data.json` and `runs/<id>/data.json`) is tracked via Git LFS — sizes range from a few hundred KB to ~98 MB. After cloning:

```bash
git lfs install     # one-time per machine
git lfs pull        # materializes the data.json files for the current branch
```

Without LFS pull, `data.json` files will be 1-line pointer stubs (~130 bytes each); the desktop will fail to read them. The `.gitattributes` rule (`**/data.json filter=lfs diff=lfs merge=lfs -text`) is committed; new commits to `data.json` automatically go to LFS.

**Bandwidth note:** the corpus is ~540 MB of LFS objects. Fresh clones eat the same against `oramasearch`'s monthly LFS bandwidth quota — confirm the org has paid LFS data packs before wiring this into CI that clones often.

## Conventions

- **Don't hand-edit individual app dirs.** They're regenerated as a batch from the synthetic-data-lab pipeline; manual changes get blown away on the next regen.
- **Slug naming**: lowercase-kebab; descriptive of the report shape.
- **Category labels are author-stamped** in `meta.json` → `events[].detail` (`Created for X` or `Generated for X`). To add a category, regenerate; don't relabel by hand.
- **Author is `Codex`** — these are not human-authored. Treat the data shape as canonical for testing but don't ship the prose / numbers verbatim to a customer screen.

## Regenerating the index

`apps.json` and the per-category READMEs are derived artifacts. To rebuild them after the corpus changes:

```bash
python3 scripts/build_index.py
```

The script:

1. (One-time) moves any apps from a legacy `data_app_synthetic/` root into `apps/<category-slug>/<slug>/`. Idempotent — no-op if `data_app_synthetic/` doesn't exist.
2. Rebuilds `apps/<category-slug>/README.md` for every category from the current state of each app's `spec.json` and `meta.json`.
3. Rewrites `apps.json` at the repo root.

Re-run any time you want to refresh the indexes. No flags needed.
